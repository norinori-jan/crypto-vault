# VAULT SECURITY DESIGN

## 概要

VAULT は **エンドツーエンド暗号化（E2EE）** の設計理念に基づいています。ユーザーのデータはクライアント側で暗号化され、サーバーは**暗号化済みデータのみ**を保持します。

---

## セキュリティ層

### 層1: クライアント側暗号化

**マスターパスワード**
- 最小4文字（推奨: 12文字以上）
- PBKDF2-SHA256 で鍵導出（200,000 反復）
- ローカルメモリにのみ保持（IndexedDB には暗号化済みで保存）

**Vault 暗号化**
- AES-256-GCM
- 毎回異なる salt (16 bytes) を生成
- 毎回異なる IV (12 bytes) を生成
- 認証タグ自動生成（改ざん検出）

**生体認証（デバイス固有）**
- WebAuthn/FIDO2
- credential ID から SHA-256 ハッシュを導出
- マスターパスワードをローカルキーで暗号化
- 別デバイスではアクセス不可

---

### 層2: ブラウザ環境

**LocalStorage の使用なし**
- 機密情報（マスターPW）は保持しない
- Worker URL のみ保存（公開情報）

**IndexedDB 暗号化**
- 暗号化済みデータのみを保存
- key-value store（平文キーを使用）
- ブラウザ同期: iCloud Keychain (iOS), Edge Sync (Windows) など

**ネットワーク通信**
- HTTPS 必須
- 平文パスワードをネットに送出しない
- HIBP チェック: k-Anonymity 方式

---

### 層3: サーバー側（Workers）

**Cloudflare Workers**
- 暗号化済みデータのみを KV ストアに保存
- サーバー側で復号化不可
- TTL（自動削除）で有効期限管理

**ログとモニタリング**
- アクセスログは最小限
- ユーザー個人情報を記録しない

---

## 暗号化スペック

### AES-256-GCM

```
モード: Galois/Counter Mode (GCM)
鍵サイズ: 256-bit
IV: 12 bytes（96-bit）
認証タグ: 128-bit（自動生成）

特徴:
- 認証付き暗号化（AEAD）
- 改ざん検出
- 並列処理可能
```

### PBKDF2-SHA256

```
アルゴリズム: PBKDF2 (Password-Based Key Derivation Function)
ハッシュ: SHA-256
反復回数: 200,000（2024年推奨）
出力: 256-bit

計算時間: 〜100-200ms (モダンCPU)
攻撃耐性:
- ブルートフォース: 10^9 回の試行でも数日要する
- GPU攻撃: 反復回数で対抗
```

### SHA-1 (HIBP用)

```
用途: Have I Been Pwned API
プロトコル: k-Anonymity
- 先頭5文字のハッシュのみ送信
- 残り35文字はローカルで確認
- 実パスワードは送信されない ✅
```

## 鍵管理

### マスターパスワード

| 項目 | 仕様 |
|------|------|
| 保存場所 | メモリ（アンロック中のみ）|
| 復号時 | PBKDF2 で毎回導出（同じPWなら同じキー） |
| バックアップ | IndexedDB に暗号化済みで保存 |
| 変更時 | 全Vault を再暗号化 |

### 生体認証キー（デバイス固有）

| 項目 | 仕様 |
|------|------|
| 導出方法 | credential ID → SHA-256 ハッシュ |
| 保存場所 | デバイス内蔵の認証器（抽出不可） |
| 用途 | マスターPW の暗号化のみ |
| 別デバイス | アクセス不可（credential ID が異なる） |
| 削除時 | IndexedDB から削除、再登録要求 |

### 共有用キー

| 項目 | 仕様 |
|------|------|
| 生成方法 | マスターPW or 別パスワード |
| 有効期限 | 1時間～7日 |
| サーバー側 | 暗号化済みデータのみ保持 |
| 受信側 | 別途パスワード入力で復号化 |

## 攻撃シナリオと対策

### 1. ブルートフォース攻撃（マスターPW）

**リスク**: オフライン攻撃でマスターPW を推測

**対策**:
- PBKDF2-SHA256, 200,000 反復
- ローカル計算 (~100-200ms)
- 10,000 回の試行 = 16-33 分（実用的でない）

---

### 2. レインボーテーブル攻撃

**リスク**: 事前計算済みハッシュテーブルからPW を復元

**対策**:
- 毎回異なる salt を生成（ハッシュが異なる）
- salt は暗号化データと一緒に保存

---

### 3. 中間者攻撃（MITM）

**リスク**: ネットワークを傍受されてデータ盗聴

**対策**:
- HTTPS 必須
- 平文パスワードは送出しない
- HIBP チェック: k-Anonymity

---

### 4. デバイス盗難

**リスク**: iPhone や PC の盗難でデータアクセス

**対策**:
- 生体認証ロック（指紋・顔認証）
- デバイス OS の暗号化（iOS, Windows bitlocker）
- IndexedDB は暗号化データのみ

**盗まれた場合の実損**:
- ロック画面をクリアされれば、IndexedDB は平文で読める
- ただし IndexedDB には暗号化済みデータのみ
- マスターPW がなければ復号化不可
- 生体認証登録キーはデバイス内蔵（抽出不可）

---

### 5. サーバー侵害

**リスク**: Cloudflare Workers が攻撃されてデータ盗難

**対策**:
- サーバーには暗号化済みデータのみ
- 暗号化キーはクライアント側（サーバーにない）
- サーバー侵害でも復号化不可

---

## 共有機能のセキュリティ

### フロー

```
送信側:
1. エントリを選択 → パスワードで暗号化
2. Workers に暗号化データのみを POST
3. Worker が share ID を生成
4. 共有 URL = 自分のサイト?s=<shareId>

受信側:
1. URL を開く → share ID で Worker から暗号化データを取得
2. パスワード入力 → クライアント側で復号化
3. データ表示（サーバーは見えない）
```

### セキュリティ保証

- **送信側**: マスターPW or 別パスワードで暗号化
- **サーバー**: 暗号化済みデータのみ保持
- **受信側**: URL + パスワード の2要素が必要
- **傍受対策**: HTTPS で URL を保護
- **自動削除**: TTL で有効期限を設定

## 監査可能性

**暗号化方式**:
- WebCrypto API（ブラウザ標準）
- NIST 推奨アルゴリズム
- ソースコード公開予定

**セキュリティレビュー**:
- 定期的な外部監査推奨
- ペネトレーションテスト推奨

## セキュリティベストプラクティス

**ユーザー向け**:
1. マスターパスワードは 12 文字以上、複雑に
2. マスターパスワードはメモ帳に保存しない
3. 定期的にパスワードを変更
4. 共有リンクは信頼できる人にのみ送信
5. 生体認証を有効化

**管理者向け**:
1. HTTPS は必須
2. Workers の環境変数を安全に管理
3. ログを最小限に保つ
4. 定期的なセキュリティ更新
